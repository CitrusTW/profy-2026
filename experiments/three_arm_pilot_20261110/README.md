# 先做一个三组小实验

**这轮已跑完, 但不是有效的三组方法对照. 具体数字看[RESULTS.md](RESULTS.md).** 更新候选超过长度限制, 第三组退回原skill; 首版共同经验还夹带了skill片段, 让no-skills不干净. 这轮不能补进论文作为CogniLife提升证据. 当前代码已修复共同经验和回传解析, 没有用修复版付费重跑.

这份代码想先把一件事做完整: 一个AI拿着原来的做事说明练习, 从真实执行里提出修改, 检查修改后有没有变差, 然后拿另一道题考试.

这里是本次新写的研究原型, 参考论文§3.4的候选修改、检查、再启用思路. 它不是袋袋原生evolution, 也不是已经证明有效的论文完整方法. 这次不测跨expert归因.

## 三组分别拿什么

| 名字 | 拿到什么 |
| --- | --- |
| no-skills | 原题和相同开发经验, 不给本项目expert包 |
| with-skills | 同样原题和经验, 再给收到的初始expert包 |
| with-skills-cognilife-method | 同一起点, 再运行本次实际更新原型; 通过检查才使用新版skill |

这里no-skills只表示没有本项目expert包. 袋袋平台本身仍提供基础指令和工具; 空skills参数不保证云端没有其他基础skill. 代码记录可见skill工具调用, 不把看不到的内部状态写成已清空.

三组都用Profy API的gpt-6.1-sol, 每次开自己的session/sandbox. 同一expert identifier作为运行入口. 初始包选收到的01-财务报销管家, 保留原文件, 不改Soul或身份.

## 练习题和考试题

- 练习: SkillsBench的pdf-excel-diff. 核对旧PDF员工记录和新Excel记录.
- 考试: SkillsBench的invoice-fraud-detection. 核对发票、供应商和采购订单.

它们都是文件核对, 但不是同一道题. 这只是一次跨任务小跑, 不能据此说已经验证所有财务工作或长期学习. 练习任务虽然处理员工记录, 用的是财务包可复用的记录核对做法, 不把它写成真实财务生产样本.

考试题的答案、隐藏测试、原评分反馈不会进入更新. 当前代码只让三组共享公开开发题面和运行统计. 已执行的首版共享过工具输出片段, 导致no-skills间接读到skill内容; 本轮缺陷和修复时间见RESULTS.md.

## 第三组真的做了什么

1. 原expert做一次练习, 在本地保存真实工具结果和输出.
2. OpenRouter的openai/gpt-4.1-mini只看公开开发题题面、通过/失败数量、耗时和工具调用次数, 提一个通用工作步骤候选. 私有expert原文、工具结果原文和答案不发给OpenRouter. 原skill只在本机用于体积比较;候选名称在本机填入.
3. 候选先过名称、长度和内容检查. 过了才再做一次同样练习, 用原pytest评分. 本轮候选在长度检查就被拒绝, 没有再做这次练习.
4. 原型只在两项都成立时采用: 开发测试通过数量不下降; skill的UTF-8文件字节数减少.
5. 保存决定和版本后, 才开始三组考试.

这里的字节数只是一种明确的文档体积指标, 不是模型token数, 也不保证更省钱或更快. 时间和真实usage另外记录. 首版代码在候选没通过时保留旧版继续运行, 因而没完成有效的第三组更新对照. 当前v2代码已改成没采用新版就停止测试, 不再用旧版冒充第三组.

这是新增研究实现. 本轮实际执行的是初始练习、候选生成和拒绝、冻结后的新题测试, 没有执行候选复测, 不冒称复现了产品全部机制.

## 长度限制从哪来, 现在怎么处理

不是Profy API限制. 论文§3.4把skill-text length作为context footprint的指标, 并对质量组和效率组的汇总指标设准入条件. 本助手把它简化成了“新版skill的UTF-8字节数必须减少”, 这是本次原型额外选择的硬条件, 不是论文规定只能写1191字节.

1191来自这一个初始skill的实际文件大小. 首版给正文留了1085字节预算, 模型返回1420字节正文, 加上105字节的固定头部是1525字节. 代码只请求一次, 超限便抛错, 外层又直接回退, 没有先让候选缩短. 这是本助手的流程处理问题.

当前v2仍保留已公开的长度门槛, 不看完测试成绩再放宽它, 但增加一次开发阶段的修改机会: 把超出多少字节告诉生成模型, 要求完整改写得更简洁, 不直接截断内容. 最多两次生成请求. 有合规候选后才做开发复测; 如果仍不合规或复测不通过, 保存原因并停止, 不启动三组新题测试. 候选变短也不等于已经复现论文完整方法.

## 修正版运行前的检查

本次仍用原来的两道题, 不把以前见过的测试题说成全新未见题. 更新器只看公开开发题和开发运行统计, 不接收测试题答案、失败原因或分数. 本轮修复范围是共同经验不再夹带skill、候选生成先要求简洁、超长时允许一次修改、拒绝后不假冒第三组, 以及检查实际skill读取. 不向更新器提供先前测试题里采购订单号的失败信息.

每次有expert包的任务必须用原生read读expense-record-reconciliation/SKILL.md全文, 并通过bash对实际文件计算SHA256. 本地检查原生read返回是否包含预期全文、哈希是否一致. 第三组还必须与初始skill哈希不同. 这些记录证明正确版本被上传和读取, 不能单独证明模型每一步都遵循了该skill.

## 怎么运行

专家包、benchmark和keys都在仓库外面. 这份仓库不提供、也不上传这些文件.

```bash
python -m unittest -v test_pilot.py
python pilot.py --workspace /path/to/CogniLife --out /path/to/local-results --dev-inputs /path/to/pdf-excel-inputs --keys-file /path/to/private-keys.md
```

上面的第二条只是显示配置, 不读key、不调用模型. 确认后在末尾加`--run`才会付费执行. 本轮用户已要求自动运行, 实际启动记录留在结果目录.

所需输入是现有SkillsBench任务目录、收到的expert目录、练习题Dockerfile指定的两份原输入. 评分使用原pytest, 只映射本地路径, 不改断言. 当前研究机器已有pytest和rapidfuzz;评分进程从现有临时环境读取. 换机器运行时需要相同依赖, 不用租GPU.

## 费用和停止

首版实际用了4次Profy任务和1次OpenRouter请求. 当前v2上限是5次Profy任务: 2次练习、3次考试; 最多2次OpenRouter候选生成请求, 第二次只在候选不合规时修改. 每次Profy任务900秒超时, 超时会请求停止. Profy任务和网络错误不自动重试, 不为高分追加调用. 三组考试最多同时跑2个. 总Profy货币账单取不到时写未知, 不写USD0; OpenRouter费用以各次返回的usage合计. v2没有自动启动.

## 到哪里看结果

结果在`--out`指定的本地目录: summary.json是总结果, gate.json是候选是否采用, 各组result.json有原评分、耗时、输出hash. 原文件、第三方评分代码和完整日志不提交到这个仓库. 仓库只保留本助手写的代码、说明和不含原文的结果摘要.

原程序的strict分数是整道任务通过=1、没通过=0. pytest通过项数只是诊断, 不是字段准确率. 一个考试task只能提供一次小样例证据, 不做显著性或广泛泛化结论.

pilot.py、test_pilot.py、recover_outputs.py和analyze_results.py是本次新写. 后两份只处理已保存的数据, 不调用模型, 专门用于本轮首版记录; analyze_results.py会拒绝把首版结论套到v2. archive/只保存此前本助手写过、未用于论文的研究脚本. 不含袋袋源码、expert文件、benchmark题面/附件/答案、官方grader或他人代码. 相关来源只写外部路径和出处, 不把内容复制进来.
