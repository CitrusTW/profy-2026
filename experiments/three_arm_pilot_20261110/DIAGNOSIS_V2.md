# 为什么三组答案相同, 这次究竟测了什么

结论: 已有日志和本地核对支持“三组各自计算后得到同一结果”, 没发现本地代码把一组答案复制给另外两组. 但第三组没有按原论文的skill evolution实现, 本次设计不能检验原论文方法的效果. 把它命名为with-skills-cognilife-method过于宽泛, 应理解为“自写prompt生成通用步骤, 再用开发题检查后替换一个skill的原型”. 历史目录名和原数字保留, 不改写实验记录.

这轮诊断新增模型调用0次. 没改原答案、原评分或论文. 仅检查已经保存的请求和工具记录, 并在本地执行已有的三份解题Python程序, 核对文件取回是否出错. 本地执行不调用Profy、OpenRouter或其他模型.

## 答案是不是被复制了

三组session不同, 解题程序的SHA256也各不相同. 三份程序都直接读取各自任务中的invoices.pdf、vendors.xlsx和purchase_orders.csv, 自己写出报告. 它们没有读取别组答案, 也没有硬编码整份交付JSON. 各组自己的bash文件导出、最终声明的SHA256和本地保存文件一致. 在本地给这三份已有程序同样的三份原附件, 三份程序又分别生成了与各自云端结果字节相同的JSON.

| 组别 | 解题程序SHA256前12位 | 本地计算与该组云端结果一致 |
| --- | --- | --- |
| no-skills | 4c8fc2105135 | 是 |
| with-skills | 9e394d1db891 | 是 |
| with-skills-cognilife-method | c5b13a5f3e4e | 是 |

这排除了已检查范围内的答案复制、取错组文件、旧导出片段覆盖新答案等本地错误. 它不能核实Profy后台所有内部状态或物理机器隔离.

## 为什么不同程序会交出相同答案

invoice-fraud-detection的题面已经把判断规则列全: 供应商找不到、IBAN不一致、PO不存在、金额差超过0.01、PO供应商不一致, 并规定多个问题同时存在时的优先顺序和JSON字段顺序. 三份程序虽然使用的库、名称匹配阈值和检查细节不同, 核心判断都来自这些相同规则. 它们又都按页遍历、按相同字段顺序写JSON, 使用相同缩进并加结尾换行. 因而在这份数据上得到相同结果, 连字节也可以相同.

对这一个model和这一道题, no-skills已经找齐参考答案标出的50张异常发票, 没漏报或多报. 另外两组没增加新的异常识别结果. 更合理的解释是: 这道题的判断规则已由题面提供, 附加skill没有在最终结果上显示增益. 现有记录不足以判断模型完全没用skill, 更不能判断skills对其他任务都没用.

## 为什么整题分数又都是0

三份程序都把发票里的PO文本原样提取出来. 找不到相应订单时标记Invalid PO, 但仍在po_number里保留PO-INVALID. 五处分别在第4、8、15、38、45页.

题面说PO缺失时写null, 但没有明确写“格式不合法的PO文本也要丢弃”. 原oracle/solve.sh只用数字形式的PO正则提取订单号, 所以PO-INVALID无法匹配, 变成None; ground_truth.json也在这五处要求null. 三组因此以同一种方式与gold不一致. 原评分整题内容检查失败, strict均为0.

这说明本轮0分被同一个PO字段表示差异卡住, 不是没有识别出异常发票. 这是题面解释和参考实现之间需要说明的边界; 不能据此直接宣布原grader有bug. 没有把PO-INVALID改成null来重新报高分.

## 第三组与论文到底有什么关系

核对依据是工作区的提交版PDF第4页, §3.4 Creator-Controlled Refinement, 以及收到的Profy-main快照中的evolution_log.py. 提交版PDF的SHA256是dce538935e9c911415b305f62e9413626f0fd82ecf28504af78b451a6ecf4819. 下面说的是这份论文和收到的代码, 不假定已核实线上部署版本.

| 原论文里的部分 | 本次实际做了什么 | 对得上吗 |
| --- | --- | --- |
| Candidate formation: 针对expert-capability gap提出程序性修改 | 原skill开发题已11/11通过. 没分类失败原因, 更新器也没看到失败轨迹 | 没实现这个触发和诊断过程 |
| 改进已有skill | OpenRouter只收到公开开发题、测试通过数量、耗时、工具调用数; 没收到原skill正文. 它另写一段通用记录核对步骤, 替换原文件 | 不是对原skill问题的诊断式修订 |
| quality-group不下降, efficiency-group严格增加 | 自写Python只查一题pytest通过数量不下降、UTF-8字节数减少 | 不是原来的组级rubric |
| context_footprint指标 | 本次按字节1191→1105判定改善. 原代码按字符数计分, 3000字符以内都是100分; 两份文件的517和1105字符在该函数下都是100分 | 本次7.2%的字节变化没有对应到原指标提升 |
| 先保留候选、评估, 再控制启用 | 本地开发复测后冻结文件, 用替换后的expert.zip启动另一session | 只借用了“候选、检查、再启用”的外层思路; 没调用原平台staging、authority或promotion流程 |
| Scoped maintenance, Crystallization, Cross-Expert Attribution | 没有做作者证据归属、跨expert对话提取、Profile/Journal路由、记忆合并或撤销 | 没测试这些部分 |

因此, 核心候选确实来自本助手自写的prompt. 外面加了实际开发执行、原程序评分、文件替换和读取检查, 所以不只是口头说“Full”; 但这些包装没有使它变成原论文的实现. 本助手不应把第三组名称或14项执行检查通过写成原方法已被验证.

## 设计为什么不能回答原来的研究问题

- 开发题从一开始就全通过, 没有展示需要学习解决的能力缺口. 更新器只看通过数量, 无法知道原skill哪里需要修.
- 原skill讲票据、费用、报销申请、历史claim_id和状态核对. 新版主要讲两份数据按稳定ID比较删除和修改记录. 它丢掉了原来的领域限定, 不是已证明保持原有能力的压缩.
- 原文主要是中文, 新版是英文. 字节减少7.2%, 字符数却从517增到1105. 这两个变化都不能直接替代真实token、执行步骤或计费成本. 原代码另外两个效率维度也没有评估.
- 测试题需要的异常判断规则已经全在题面里. 更新后skill没有提供能区分三组的PO表示规则. 三组业务判别相同, 唯一失败类型又相同, 单题strict无法说明原方法的收益.
- no-skills与with-skills之间加的是整个expert包, 包含identity、Soul、instructions和其他资料; 不是只开关一个skill. 第二组与第三组确实只改了一个文件, 但不能把第一组与第二组的差异单独归因于skills.

附带发现一个路径适配限制: no-skills在云端的解题程序只写outputs/fraud_report.json, 另外两组还写会话根目录的fraud_report.json. 本地driver会把导出字节存到统一文件名后运行映射路径的原grader. 因而当前分数是对取回交付件的原脚本内容评估, 不能冒称整个原生SkillsBench环境和文件路径验收都已复现. 这不解释三组内容相同, 也没有改变本轮strict均为0的结论.

## 现在可以怎么说

可以说: Profy API能够在分开的session里加载不同的文件版expert, 新版skill全文已读到, 三份独立程序在这道发票题上给出相同结果. 原评分均未通过, 同样卡在5个PO字段表示上.

不能说: 原论文方法已被实现; skill evolution有效或无效; CogniLife没有帮助; 文档字节变少就证明效率提高; 这轮补上了跨expert或长期学习的缺口.

当前主要问题是本助手的实验实现与论文方法没有对齐, 加上单题设计缺少可以区分方法收益的信号. 没有证据支持把相同答案直接归咎于Profy没有加载skill. 本轮不应作为原论文方法效果的证据. 本次不安排任何新的付费运行.

复核事实见AUDIT_FACTS.json和ORIGINAL_FOOTPRINT_CHECK.json. audit_v2.py只读取已有文件; 本地程序核对需要显式指定--replay-reviewed-local-solvers, 不调用模型. 第三方原文、原oracle、原grader和三份解题程序未复制进代码仓库.
